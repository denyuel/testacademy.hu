Day 2: Full-Stack Integration Testing Mission

Today, you step beyond isolated testing. You will master the E2E Triangle: triggering transactions on the Frontend UI, inspecting and manipulating endpoints via the Interactive API Swagger Console, and directly querying and validating data persistence in the Live SQL Database.

Launch Full-Stack App ↗
🎯 Architecture Overview for Today:
The Full-Stack Sandbox contains 3 interactive tabs running on a single shared reactive backend:
• Tab 1 (Storefront UI): Real-time checkout form & live order tracking table.
• Tab 2 (API Swagger Console): Execute REST endpoints (`GET`, `POST`, `PATCH`, `DELETE`) with role-based auth and status codes.
• Tab 3 (Live SQL Database): Run actual SQL queries (`SELECT`, `JOIN`, `UPDATE`, `GROUP BY`) against the shared database engine!
🆘 If You Get Stuck – The 4-Step Professional QA Protocol:
1. Use Built-in Sandbox Clues: On the SQL tab, check the Database Schema Reference card and Quick Query Chips. In Swagger, review the pre-filled sample JSON payloads.
2. Check Your Repo Notes: Open 05_sql_queries_for_qa.md in your local Git repository for exact query syntax examples (Joins, Duplicate Checks, Aggregations).
3. Use AI as a Technical Dictionary / Encyclopedia (Not for cheating!): Ask conceptual questions like: "What is the SQL syntax for a LEFT JOIN when checking for NULLs?" or "What triggers HTTP 409 Conflict in a REST API?".
4. Ask Mentor Daniel like a Pro: If stuck for more than 5 minutes, ask Daniel with context: (a) which task you're on, (b) what you tried, and (c) what error you received!

PART 6 Senior Bonus Challenges / Bug Bounty Hunter 🏆
7 Advanced Tasks
6.1. SQL Injection (SQLi) Probe in Input Fields
Test whether user input fields in Storefront and API sanitize malicious SQL payloads.
Steps:
  1. In Tab 1 (Storefront), enter the classic SQL injection string into the Email field:
    ' OR '1'='1 or test' OR 1=1; --
  2. Click Place Subscription Order. Notice client-side HTML5 email validation blocks invalid email strings.
  3. Now bypass UI validation using Tab 2 (Swagger): in POST /api/v1/orders, send payload with:
    {"email": "admin' OR '1'='1", "product_id": 1, "quantity": 1, "price": 99}
  4. Check if the backend crashes, escapes the string safely, or executes unexpected logic.
❓ Question: How did the UI vs Swagger API handle the SQL injection attempt? Did the backend crash or safely escape/reject it?
6.2. Orphaned Data & Referential Integrity Audit
Investigate what happens to child records in relational tables when parent records are deleted without cascading foreign key constraints.
Steps:
  1. In Tab 3 (Live SQL), delete user #1 directly:
    DELETE FROM users WHERE id = 1;
  2. Now run a JOIN between orders and users:
    SELECT orders.id, orders.user_id, users.email FROM orders INNER JOIN users ON orders.user_id = users.id;
  3. Notice what happened to Order #101! It now references a deleted user (orphaned child record).
❓ Question: In enterprise relational databases (PostgreSQL/MySQL), what database constraints or architecture prevent orphaned orders (e.g. ON DELETE CASCADE, foreign key constraints, or soft deletes)?
6.3. Integer Boundary & Negative Quantity Exploit
Attempt to submit negative, zero, or extreme integer boundary quantities to uncover business logic bugs.
Steps:
  1. In Tab 2 (Swagger), in POST /api/v1/orders, set quantity to -5 and click Execute.
  2. Then try setting quantity to 0, and finally to 9999999999.
  3. Check status codes and the resulting total calculation.
❓ Question: Does the backend allow negative orders (e.g. paying negative money or artificially increasing inventory)? What validation rule should be added?
6.4. Custom SQL: Inactive Users with Zero Orders
Write a SQL query to identify registered accounts that have never made a purchase.
Steps:
  1. In Tab 3 (Live SQL), write a query using LEFT JOIN to find users with no corresponding orders:
  2. SELECT users.id, users.email FROM users LEFT JOIN orders ON users.id = orders.user_id WHERE orders.id IS NULL;
  3. Click ▶ Run Query.
❓ Question: Which user(s) returned with zero orders? Why is LEFT JOIN ... WHERE ... IS NULL standard practice for churn and marketing audits?
6.5. Custom SQL: Revenue & Financial Aggregation
Calculate total verified revenue from paid orders in the database.
Steps:

  2. SELECT SUM(total) FROM orders WHERE status = 'PAID';

❓ Question: What is the exact total revenue from PAID orders? Why must QA reconcile database aggregates against UI analytics dashboards?
